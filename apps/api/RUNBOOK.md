# Phase 1 API and worker operations

This service implements project ownership, immutable revision history, bounded private intake, asynchronous conversation normalization, thread selection and candidate review. It requires PostgreSQL and trusted short-lived bearer tokens signed by the web server. It does not accept a browser supplied user ID.

## Runtime boundaries

The web server signs an HS256 token for issuer schemora-web, audience schemora-api, stable subject and a maximum five minute lifetime. The API verifies signature, issuer, audience, issued time and expiry. Production accepts GitHub numeric subjects only. API project queries include the authenticated owner. Nested import and revision reads also include project scope. A guessed identifier returns the same unavailable response as a missing resource.

The API handles synchronous lifecycle commands. The separately scalable worker claims PostgreSQL jobs through SKIP LOCKED and uses a token fenced lease. API mutations insert the outbox intent in the same transaction as canonical state. Dispatch inserts a job and marks its outbox row delivered atomically. Duplicate dispatch does not insert a second job. Workers renew their lease without overlapping heartbeat queries; stale owners cannot apply results after another worker takes over.

Every canonical mutation includes an integer expectedRevision and a UUID Idempotency-Key header. Project head advancement, immutable revision insertion, review history and outbox writes commit in one database transaction. Reusing an idempotency key with another payload returns a conflict. Project creation uses a transaction advisory lock; subsequent writes lock only the target project. Authorized reads hold a shared project lock while loading related records.

Environment values are validated before listening. Errors name invalid settings without printing their values. API handlers return stable safe errors and do not serialize object keys, source bytes, tokens, database diagnostics or exception stacks. Worker routine logs contain only an event and job type.

Production deployment requires a documented private bucket policy, public access block, restricted service IAM, encryption and retention behavior. The SDK obtains credentials through its normal provider chain. PutObject uses an immutable generated key, a server computed SHA256 checksum and an if-none-match condition. Reads verify byte count and digest. Object lock retention that prevents deletion must be reconciled with the product retention policy before enabling it.

## API contract

Success responses contain data and requestId. Errors contain error.code, error.message, error.retryable and error.requestId. Revision conflicts additionally return currentRevision. Timestamps are UTC. Project states are active, archived and deleting; deleted tombstones are unavailable through ordinary APIs.

Uploads are at most 10 MiB of decoded bytes. The API accepts txt, md, html, pdf, json and zip names only, rejects noncanonical base64 and unsafe path names, and limits one project to 20 imports. Unsupported content fails during bounded inspection; acceptance of bytes does not imply successful parsing. Multiple conversations remain separate and require explicit thread selection. Bundle and selected conversation warnings are exposed. Only selected conversation messages reach extraction.

Firmware source has a separate 2,000,000-byte limit and accepts UTF-8 text only. Supported languages are C, C++, Arduino C++, and ESP-IDF C; the entrypoint extension must match the selected language. The API resolves exactly one development board from the saved graph and current catalog and ignores any client attempt to supply board, catalog, digest, byte length, review state, or storage location. New source is pending review. `accepted` means the project owner explicitly chose that version for future runs; it does not mean code passed a security review, compiled, or is safe. The metadata revision is the revision created by the upload mutation, while the artifact records the exact board and catalog release. Its source digest and artifact ID are later bound separately from the graph revision/digest in any run.

The private-storage package keeps the existing 10 MiB source-object bound and adds a separate compiled-build object interface capped at 64 MiB per binary. The build interface verifies exact expected byte length and SHA-256 on read; it does not raise source upload limits. Migration `0011` adds immutable source/profile-bound build metadata and binary manifests. Authenticated owner-scoped read routes return normalized diagnostics/manifests or stream one verified binary with `Cache-Control: no-store`; object keys are never returned. Project purge includes build objects and removes their metadata only after object deletion. A worker helper reconstructs only the owner-scoped, currently accepted ESP-IDF source bundle from immutable file records, verifies each object digest and length, and recomputes the canonical manifest before compiling. Under the current built-in-components-only profile policy, the compile boundary rejects `idf_component.yml`, `idf_component.yaml`, `dependencies.lock`, and any `managed_components/` subtree. This path guard blocks the direct Component Manager dependency declarations but cannot prove that arbitrary CMake or component code performs no downloads; network denial must be enforced by the isolated runner. The profile schema is not a trusted profile registry, and the helper is not wired to worker jobs. It then stages verified outputs under durable upload intents and atomically commits build metadata and manifests in PostgreSQL; persistence rechecks the latest accepted review under the project lock. Object storage and PostgreSQL are separate systems: if persistence fails ambiguously, staged objects remain tracked by their intents for expiry cleanup. A production-eligible compiler sandbox, trusted profile resolver, job dispatcher, and production caller are not connected, so the routes currently return empty build history and no compile request is accepted.

Simulation run creation accepts only `expectedRevision` and `firmwareArtifactId`; it does not accept caller supplied run output, binding, graph, validation or provider fields. The API holds the project lock while resolving the graph snapshot at the expected project head, its matching current-catalog validation report, and the artifact's latest accepted review. It revalidates the report against the pinned graph/catalog, persists the immutable binding and queued run, writes an outbox intent and records the idempotency response in the same transaction. A project may have at most three queued runs and the service at most 100 queued runs. The binding records the graph snapshot ID/digest/revision, catalog release/digest, firmware ID/digest, and the configured adapter/engine identity. The current values `schemora.unconfigured` and `none` explicitly mean no provider is approved. The worker completes these jobs as `SIMULATOR_UNAVAILABLE`; queueing a run does not claim compilation or execution.

## Firmware execution isolation gate (not integrated)

**Current state:** the simulation worker intentionally settles runs as `SIMULATOR_UNAVAILABLE`. A worker-side Docker launcher module has unit coverage for fail-closed host/image checks, fixed argv, limits, and cleanup, but it is not wired into run jobs and does not establish a deployed sandbox. The worker does not fetch firmware bytes, launch a process/container, or invoke a simulator. The following is a production deployment contract for a future isolated execution service. Do not configure the ordinary API or worker to run customer firmware.

The shared simulation package now defines a strict versioned runner request/response contract and a signed response envelope. Requests carry the frozen graph, catalog, validation report and digest, firmware reference/review revision/source, exact run binding, fixed administrator profile ID, deadline, payload digest, and an expiring Ed25519 capability bound to run ID, attempt ID, audience and one-use token ID. The isolated runner must verify the firmware SHA-256 against both the artifact reference and run binding, match the request against its local profile allowlist (image digest, adapter/engine versions, board/components/topologies and hard resource limits), verify the capability with its configured public-key ring, and claim the token ID through an atomic replay guard. The runner response verifier checks an Ed25519 signature, exact response digest, run/attempt/payload/profile/image/binding/request-token binding, issued time, cleanup ordering, bounded post-deadline reporting grace, and response-token replay claim. Migration `0009` adds a durable run-attempt ledger. Persistence APIs create and load lease-bound attempts and accept a caller-verified response in one transaction that rechecks the active project, current lease and attempt, run binding, legal status transition, and replay JTI before updating the run, attempt and terminal job state. PostgreSQL integration coverage verifies signed response acceptance, duplicate rejection and stale response rejection after lease reclaim. The worker package now exposes `acceptRunnerResponse`: it loads the current leased attempt, checks its trusted profile and image digest, verifies the signed response against persisted attempt identity and timestamps, then delegates acceptance to the atomic persistence API. No transport or job path invokes this boundary, and it does not build or dispatch requests. Sandbox-runner adapters bind capability and response claims to separate issuer namespaces and token classes. No runner HTTP service, provisioned production public keys, production replay-store pool, worker dispatch client, or trusted profile configuration exists; dispatch remains disabled.

The response cleanup receipt is a typed runner claim. The new signed envelope provides message integrity and authenticates the signer only when the verifier uses securely provisioned runner public keys; those keys are not configured here. Before integration, provision and rotate runner-only signing keys or add verified mTLS workload identity, use a durable shared replay store, and enforce run/attempt replay and lease fencing. The runner control plane must derive the receipt from observed process termination, runtime-object removal and workspace removal, and deployment validation must exercise those paths. Even an authenticated receipt does not prove that host isolation controls were enforced.

The execution service must run on a separately administered Linux host pool behind a narrow authenticated job gateway. Use a rootless OCI runtime with cgroup v2 resource controllers delegated and verified, or a stronger microVM boundary for untrusted firmware. A rootless Docker daemon still exposes a powerful control API to its socket owner, so only the isolated runner service may access its private socket; never mount the socket into a job container or give the general API/worker Docker-group or daemon credentials. A rootful Docker daemon grants its control users host-level power. Containers also share the host kernel, so rootless mode reduces host privilege but does not remove kernel attack-surface risk; prefer a microVM when the threat model requires a separate guest kernel.

Before accepting a run, the runner must resolve an administrator-approved simulator/compiler image by immutable OCI digest from a local, preloaded image store. Production execution must not pull images, resolve mutable tags, build images, or contact registries. Verify the digest and supported platform at admission, and fail closed if unavailable. Pass the run ID and validated input as structured data; never construct a shell command by interpolating user-controlled source, IDs, paths, environment values, or compiler arguments. Use a fixed executable and argument vector, fixed working directory, and a pinned entrypoint.

Each run must receive a fresh disposable container or microVM with no credentials, secrets, cloud metadata access, host networking, or network egress. Disable networking at the runtime and enforce egress denial outside the guest as defense in depth. Drop all Linux capabilities, prohibit privilege escalation, run as a dedicated non-root UID, use a read-only root filesystem, and apply the runtime's default or stricter reviewed seccomp profile (plus AppArmor/SELinux where supported). Do not use privileged mode, host PID/IPC namespaces, device passthrough, or host paths. Do not mount shared host directories. If file exchange is required, mount only the generated per-run input snapshot read-only. Capture output through a bounded channel or a size-limited output filesystem, validate it, then freeze it before exposing it as a read-only snapshot. Keep scratch space ephemeral and enforce its disk quota at the runtime/storage layer.

Set and verify hard per-run cgroup limits for CPU, memory, and process count, plus wall-clock deadline, scratch-disk quota, stdout/stderr byte caps, and structured-event count/size caps. Rootless Docker ignores cgroup resource flags unless the documented cgroup v2/systemd conditions are met, so startup health checks must prove each configured controller is active; reject execution when a required limit is not enforced. The orchestrator must kill the entire container/VM and remove its workspace on timeout, user cancellation, lease loss, worker shutdown, and normal completion. Cleanup failures must be observable and retried by a reconciler before capacity is released.

Treat all runtime output as hostile. Enforce byte/count caps while reading, parse against the versioned output schema, validate event types and component identities against the frozen graph/catalog/firmware binding, and reject unknown fields, invalid references, malformed data, oversized payloads, and stale lease or snapshot identities. Only a validated result may become a completed run; every other outcome is unsupported or failed with a bounded safe diagnostic. Store no raw process environment, credentials, or unbounded logs in the run record.

Deployment evidence required before enabling a provider: isolated runner host and daemon ownership; pinned image digest and offline preload verification; enforced seccomp/LSM and cgroup settings; network-denial proof; per-run storage and output limits; cancellation and forced-cleanup evidence; hostile-output schema rejection; and an operational cleanup/reconciliation procedure. Docker's own documentation describes rootless mode, rootful daemon attack surface, shared Linux kernel isolation, seccomp, network-none mode, read-only roots and resource constraints; those features are controls to configure and verify, not proof that this project's execution sandbox exists.

References: [Docker rootless mode](https://docs.docker.com/engine/security/rootless/), [Docker Engine security](https://docs.docker.com/engine/security/), [protect Docker daemon access](https://docs.docker.com/engine/security/protect-access/), [seccomp profiles](https://docs.docker.com/engine/security/seccomp/), [container run options](https://docs.docker.com/reference/cli/docker/container/run/), [network-none driver](https://docs.docker.com/engine/network/drivers/none/), [container resource constraints](https://docs.docker.com/engine/containers/resource_constraints), and [rootless resource-limit requirements](https://docs.docker.com/engine/security/rootless/tips/#limiting-resources).

Run summaries are paged at 50 rows and omit event payloads. Single-run reads validate and return the bounded simulation contract, whose serialized result is limited to 2,000,000 bytes and 5,000 events. Cancellation accepts an empty JSON object and is allowed only while the run is queued. It atomically stores a `CANCELLED` terminal result, cancels its queued job, and marks an undispatched outbox row delivered so it cannot later create work. Archive and deletion similarly terminalize queued simulation runs and fence their queued jobs. A run that has already started cannot be cancelled through this queued-only endpoint.

Project summaries omit full extraction content. The active import endpoint contains its bounded extraction. Transcript messages are paginated and latest review summaries are capped at the candidate limit of 2000; complete history uses its own descending revision cursor.

## Canonical records and reconstruction

The reviewed SQL migration files are the database schema authority. Drizzle declarations provide typed simple reads; parameterized PostgreSQL queries implement explicit locking, queue claiming and transaction boundaries. The migration runner acquires an advisory lock, applies each migration in a transaction and checks its SHA256 ledger. Editing an applied migration is rejected; add another migration.

Each revision contains project metadata, import source IDs/digests, selected thread, immutable bundle/extraction digests, processor metadata, firmware artifact metadata references, and a reviewThroughRevision boundary. Source bytes and accumulated review histories are not copied into every revision. To reconstruct a revision, resolve project-scoped import artifacts by digest, source artifacts by immutable ID/digest, and choose the latest immutable import or firmware review decision at or before that revision's boundary. Firmware artifact rows store source digest, byte length, language, entrypoint, exact board part, and catalog release; storage keys remain server-only. A new processing policy requires a new build/version identifier.

Candidate corrections remain independent review records. They do not overwrite the extracted evidence, candidate details or normalized source. Superseded candidates cannot be accepted as current. Review acceptance records the user's choice and does not certify hardware compatibility.

## Processing limits and production gate

A parser subprocess runs with a 256 MiB JavaScript heap and a 30 second parent deadline. Its environment omits database, session, storage and provider credentials. Parent validation limits normalized output to 25 MiB and validates bundle and extraction schemas before persistence. Archive entry, expansion, ratio, nesting and path limits are owned by the intelligence package.

The subprocess is resource isolation for local development. It is not an operating system sandbox, and its heap limit is not a total resident memory limit. It does not enforce network egress denial. Before exposing untrusted imports in production, deploy the parser role in a reviewed container or equivalent runtime with no network egress, read only root filesystem, bounded temporary disk, operating system memory and CPU limits, and an unprivileged identity. Provider extraction must run in a separate permitted application role or through a controlled gateway. This gate is unresolved until that deployment evidence exists; the local subprocess must not be described as proof of production isolation.

Rules extraction explicitly describes itself as conservative candidate generation and may miss facts. A configured provider is still untrusted and source grounded, with all output requiring review. If a provider fails, the worker preserves normalized content and exposes deterministic source assistance with an explicit warning and actual extractionMode; it does not label the result provider generated.

## Failure, cancellation and deletion

Retryable processing failures use bounded exponential delay. Unsupported or invalid content fails without automatic retries. Exhausted expired leases become failed; a newer retry job prevents an older failed attempt from invalidating current processing. Manual retry creates a new durable job. Cancellation and archive cancel active job tokens; in-flight output is discarded when project/source/job preconditions are checked again.

Deletion immediately revokes reads, cancels ordinary work and creates a purge job. Purge deletes private import, firmware source, and compiled build objects (including every bundle child and every binary output), their metadata, bundle/extraction artifacts, normalized content, simulation attempt-ledger rows before their referenced run records, import and firmware review history, revisions and cached idempotency responses, then preserves a minimal project tombstone. An incomplete object purge leaves the project deleting and unavailable; it cannot be reported successfully deleted. Failed deletion jobs need operator review and requeue through a controlled operation after correcting the storage failure. Backup expiry and deletion replay are deployment obligations.

Before writing any private bytes, the API registers an authorized, durable upload intent containing the generated key, project scope and a 15 minute expiry. Successful source persistence consumes the intent in the same transaction as the import and job outbox record. A confirmed upload followed by a persistence failure removes its bytes and intent; a cleanup failure preserves the intent for retry.

An uncertain storage acknowledgement may represent a put that finishes after a timeout. The API attempts immediate byte deletion and retains that intent until expiry, so a late storage completion remains tracked. Project purge also deletes staged bytes immediately while retaining fresh intents through the same grace interval. This prevents an already-running upload from creating an untracked object after project deletion. Normal project access is revoked throughout deletion.

Worker maintenance inspects at most 10 expired intents per pass, locks each with SKIP LOCKED, deletes tracked bytes and removes the intent only after successful cleanup. Accepted import, firmware entrypoint, and firmware bundle-file objects are protected. Fresh intents are preserved, and source acceptance requires each unexpired intent to be consumed under its row lock in the artifact transaction. Bundle requests register intents for every generated object key before the first private write; a maximum-size project bundle contains 128 files. This cleanup needs no public bucket listing or full object inventory; it uses the exact private keys recorded before upload. Storage failure delays purge and leaves the durable intent available for the next pass. Backup expiry and deletion replay remain deployment obligations.

### Firmware bundle API boundary

`POST /v1/projects/:projectId/firmware-artifacts/bundles` accepts an expected project revision, build system, target, entrypoint, and base64 file contents. The API recomputes each source hash and the canonical manifest digest, verifies UTF-8 text and path rules, and derives the board/catalog identity from the current validated graph. This catalog currently maps only ESP-IDF `esp32` to the exact ESP32-DevKitC V4 / WROOM-32E board; other build targets fail closed. `GET .../:artifactId/files` returns file path/digest/length metadata, and `GET .../:artifactId/files/content?path=...` downloads exactly one authorized file after storage checksum and byte-length verification. The existing `/content` endpoint still downloads the entrypoint content and keeps its original entrypoint `sha256` and `byte_length` meaning. The worker can purge all recorded child objects. None of these endpoints invokes a compiler or makes a run executable. Bundle run bindings use the manifest digest and aggregate length. The shared runner request contract accepts and verifies full bundle contents against the artifact reference and an administrator profile's exact build-target allowlist, but no worker or transport constructs or dispatches that request; bundle execution remains disabled.

## Verification and research

Integration tests require an independently migrated TEST_DATABASE_URL. Do not share their database with a running development worker, because job transport is shared within a database while test source objects use isolated directories. Tests clean only their synthetic principals and project records.

The test suite covers trusted authentication, cross-user resource denial, idempotent replay/conflicts, concurrent writes, immutable snapshots, accepted format intake, source processing, thread selection, review correction preservation, archive/retry/cancel, stable pagination, duplicate delivery, lease fencing, exhausted lease handling, active deletion/cancellation, heartbeat renewal and provider outage fallback. Parser package fixtures separately prove supported formats and hostile input behavior.

Implementation decisions were researched against [Fastify v5 documentation](https://fastify.dev/docs/latest/Reference/), [Drizzle PostgreSQL integration](https://orm.drizzle.team/docs/get-started-postgresql), [Drizzle transactions](https://orm.drizzle.team/docs/transactions), [PostgreSQL locking clauses](https://www.postgresql.org/docs/current/sql-select.html), [S3 integrity checks](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html) and [S3 versioned deletion](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html). Stable package versions are locked; the Drizzle documentation's RC installation example is not adopted implicitly.
